# Отчёт: генератор договоров — правки на бэкенде sellico.ru

Дата: 2026-07-24. Сервер: sellico.ru, код: `/var/www/html/backend` (Laravel, PHP-FPM, LibreOffice 24.2.7.2 для конвертации). Задача: договор генерировался с пустыми полями (колонтитул с прочерками, пустая дата окончания в п. 12.1, незаполненный телефон Исполнителя, «КПП: -» у ИП), без подписи; счета выходили с реквизитами-заглушками из нулей.

## 1. Как устроена генерация (для контекста)

`POST /api/workspaces/{id}/legal-documents/generate-contract` → `WorkspaceLegalDocumentController::generateContract` → `App\Services\Legal\WorkspaceContractPdfGenerator::generate()`:

1. Берёт DOCX-шаблон `resources/templates/legal/sellico-contract.docx`.
2. Строковыми заменами заполняет все `word/*.xml` внутри DOCX (тело + колонтитулы).
3. Конвертирует в PDF через `soffice --headless`.
4. Сохраняет PDF + заполненный DOCX-исходник в `storage/app/workspace-legal-documents/{workspace}/`, пишет в БД запись `workspace_legal_documents` (sha256 обоих файлов, версия и sha256 шаблона, снапшот юрданных в metadata).

## 3. Шаблон DOCX — что изменено внутри

- **П. 12.1**: было «действует до «____» ______________ 20____ г.» (пустая дата навсегда) → стало «действует в течение 1 (одного) года с даты подписания». Формулировка самодостаточная, подстановка даты не нужна; автопролонгация из второго предложения пункта сохранена.
- **Телефон Исполнителя**: плейсхолдер `[+7 (___) ___-__-__]` в реквизитах Исполнителя заменён константой `+7 (966) 020-70-61` (реквизиты Исполнителя — не переменные). Плейсхолдер телефона у Заказчика оставлен — его заполняет код (замена последнего вхождения).
- **Новый п. 14.7** о факсимиле: «Стороны признают юридическую силу факсимильного воспроизведения подписи Исполнителя… (п. 2 ст. 160 ГК РФ)» — юридическое основание для подписи-картинки.
- **Подпись-факсимиле**: в блок подписи Исполнителя (раздел 15, над строкой «___/ Зубарев Д.В. /») вставлено изображение `word/media/signature-zubarev.png` (прозрачный PNG 1061×468, в документе 3.8×1.68 см). Исходник — присланный скан, фон вырезан порогом яркости с дилатацией маски штрихов. Также добавлены relationship в `word/_rels/document.xml.rels` (Id=`rIdSigZ`) и `Default Extension="png"` в `[Content_Types].xml`.
- Подпись Заказчика намеренно НЕ вставляется — его блок остаётся для собственноручной подписи/ЭДО.

## 4. `WorkspaceContractPdfGenerator.php` — правки

1. **Колонтитул**: в `templateReplacements()` добавлена замена `'Договор Sellico № ____ от «____» ______________ 20____ г.'` → `'Договор Sellico № {номер} от {дата}'`. Метод получил третий параметр `Carbon $generatedAt` (вызов обновлён). Колонтитулы и раньше проходили через механизм замен (`word/*.xml`) — не было самого правила.
2. **КПП для ИП**: замена строки `'ИНН: … КПП: …'` стала условной по `entity_type`: для `ip` выводится только ИНН, «КПП: -» больше не печатается.
3. **Номер договора**: `contractNumber()` теперь при повторной генерации в тот же день добавляет суффикс: первая — `SLC-3-20260724`, вторая — `SLC-3-20260724-2` и т.д. Определяется подсчётом существующих договоров workspace с номером `like 'SLC-{ws}-{Ymd}%'` по JSON-полю `metadata->contract_number`.
4. **Пост-валидация** — новый метод `assertNoUnfilledPlaceholders()`: после заполнения открывает итоговый DOCX и ищет в тексте маркеры незаполненности (`[_`, `«____»`, `20____`, `[+7 (`, `[Полное`, `[должность`, `[Устава`). Найдены → `RuntimeException` со списком «файл: маркер», генерация падает, контроллер вернёт 500 и запишет ошибку в лог — вместо молчаливой выдачи битого PDF. Вызов вставлен перед конвертацией в PDF.
5. Импорт `App\Models\WorkspaceLegalDocument` для запроса номера.

## 5. Контроллер — 1 строка

В `generateContract()` при создании записи добавлено `'document_number' => $generatedFile['metadata']['contract_number'] ?? null` — номер договора теперь хранится в колонке `document_number` (раньше только внутри JSON metadata; колонка была всегда NULL для договоров).

## 9. Дополнение 2026-07-24 (вечер): 502 на «Продлить тариф» и удаление документов

### 9.1. Диагноз 502 на `POST /api/workspaces/3/orders`

Кнопка «Продлить тариф» падала с 502. Прослежено по цепочке:

1. Заказ в БД **создавался** (orders id=22, 150 000 ₽, enterprise, status → cancelled) — значит, падала регистрация платежа в шлюзе.
2. 502 отдаёт **сам Laravel**: в `OrderController` catch `AlfaPaymentException` возвращает `$exception->getCode() ?: 502`.
3. Корень: `curl https://alfa.rbsuat.com/...` с сервера → **TLS-ошибка «self-signed certificate in certificate chain»**. Цепочка сертификатов шлюза Альфы выпущена **НУЦ Минцифры (Russian Trusted Root CA)**, которого нет в системном хранилище Ubuntu → каждое обращение к шлюзу = ConnectionException = 502.

### 9.2. Исправление (без прав root)

- В `resources/certs/` загружены официальные корни НУЦ с gu-st.ru (`russian_trusted_root_ca.crt` — срок до 27.02.2032, `russian_trusted_sub_ca.crt`), нормализованы переводы строк (в исходниках CRLF без завершающего \n — при склейке PEM ломался), собран бандл `ca-bundle-with-russian.pem` = системные CA + корни НУЦ. Проверено: `curl --cacert bundle https://alfa.rbsuat.com/...` → HTTP 200.
- `AlfaPaymentService`: конструктор читает `services.alfa_payment.ca_bundle`; если файл существует — HTTP-клиент получает `['verify' => bundle]`. Без конфига поведение прежнее (системные CA).
- `config/services.php`: добавлен ключ `'ca_bundle' => env('ALFA_PAYMENT_CA_BUNDLE')`.
- `.env`: `ALFA_PAYMENT_CA_BUNDLE=/var/www/html/backend/resources/certs/ca-bundle-with-russian.pem`.

### 9.2.1. Вторая причина 502 (найдена после TLS-фикса)

После починки TLS заказы продолжили отменяться (orders 23–25). Прямой диагностический вызов `register.do` с сервера показал: **шлюз работает, но платёжную форму отдаёт на новом домене** `uatpayment2way.com` (раньше — `alfa.rbsuat.com`). В `OrderController` есть allowlist хостов формы (`PAYMENT_FORM_ALLOWED_HOSTS`, в `.env` был только `alfa.rbsuat.com`) — «неожиданный» URL отклонялся, заказ отменялся, ответ 502.

Исправлено: `.env` → `PAYMENT_FORM_ALLOWED_HOSTS=alfa.rbsuat.com,uatpayment2way.com`, `php artisan config:cache`. Проверено в кеше конфига: оба хоста на месте, путь формы `/payment/merchants/…` проходит и по `allowed_paths`. При переходе на боевой шлюз в allowlist нужно будет добавить боевой домен формы.

### 9.3. ⚠️ Отдельно важно: шлюз указывает на ТЕСТОВУЮ среду

`ALFA_PAYMENT_BASE_URL=https://alfa.rbsuat.com/payment/rest` — это **UAT-песочница** Альфа-Банка. После TLS-фикса кнопка заработает, но деньги через песочницу не ходят. Для боевых платежей нужно получить от Альфы прод-URL (`payment.alfabank.ru`) и боевые креды мерчанта, заменить `ALFA_PAYMENT_BASE_URL`, `ALFA_PAYMENT_USER_NAME/PASSWORD` и `PAYMENT_FORM_ALLOWED_HOSTS` в `.env`.

### 9.4. Удаление документов в ЛК

- Бэкенд: новый `DELETE /api/workspaces/{ws}/legal-documents/{document}` (`destroy` в `WorkspaceLegalDocumentController`): доступ владельцу/админу; **подписанные и оплаченные документы удалить нельзя (422)**; удаляются PDF + исходный DOCX из storage + запись; действие пишется в журнал активности.
- Роут добавлен в `routes/api.php` (после изменения роутов обязателен `php artisan route:cache` — включён в скрипт применения).
- CRM-фронт (репо `front2/frontend-from-server`, деплой отдельный): метод API + кнопка удаления с подтверждением в списке «Сохраненные документы» (скрыта для подписанных документов).

## 9.6. Дополнение (ночь 24.07): ложное «оплата успешна» при отмене + вылет в логин

Симптомы: пользователь отменил оплату на 3DS-странице банка → CRM показала праздничный экран «Проверяем оплату» (читается как успех) и выбросила на логин (все API отвечали 401).

Причины (три независимых):
1. **Вылет в логин**: auth-токены CRM хранятся в `sessionStorage` (осознанное XSS-решение), но возврат с 3DS-страницы банка разрывает browsing context (COOP) — sessionStorage пустеет → 401 → редирект на логин. Бэкенд ни при чём.
2. **«Успешный» экран при отмене**: в `.env` `ALFA_PAYMENT_FAIL_URL` указывал на тот же `?payment=return`, что и успешный возврат, а `AlfaPaymentService` при отсутствии failUrl вообще подставляет returnUrl. Любой исход платежа приводил на «Проверяем оплату» в праздничном оформлении.
3. БД при этом честная: заказы 28–30 остались `in_progress`/`cancelled`, подписка не продлевалась — джоба `CheckOrderPaymentStatus` корректно различает статусы банка (2=оплачен, 3/4/6=отказ).

Исправления:
- **CRM-фронт** (репо front2): токены на время платёжного редиректа стэшируются в `localStorage` с TTL 15 минут и восстанавливаются при возврате (`tokenStorage.stashForPaymentRedirect()` + восстановление при загрузке модуля); все уходы на платёжную форму — через единый `redirectToPaymentForm()`; копирайт «Проверяем оплату» переписан без празднования.
- **Бэкенд** (пакет `apply-patches-2.sh`): `AlfaPaymentService` теперь передаёт банку отдельный failUrl из `services.alfa_payment.fail_url` (с теми же параметрами workspace/order); `.env` → `ALFA_PAYMENT_FAIL_URL=https://sellico.ru/crm/feed?payment=fail`. Отмена оплаты теперь ведёт на экран «Оплата не прошла».
